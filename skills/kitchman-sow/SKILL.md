# Kitchman SOW

Use this skill to create a Kitchman project SOW and proposal from a Feishu conversation and uploaded project materials.

## Operating Boundary

- Treat this as an SOW preparation assistant, not an automatic quotation system.
- Do not generate final prices, quote totals, or payment amounts.
- Do not present uncertain materials, dimensions, hardware, stone, lighting, lead time, or installation details as confirmed facts.
- Mark uncertain content as `TBC`, `unknown`, or an open question.
- Keep evidence visible with `source_type`, `confidence`, and source notes.
- Do not use Python scripts to parse drawings, OCR PDFs, identify rooms, extract scope, or interpret natural-language revisions in the current demo version.
- PDF drawing pages may be rendered to PNG first so the model can visually review the pages.
- Use scripts only for lightweight SOW state management, PDF-to-PNG rendering, structured JSON-to-Markdown/DOCX rendering, ZIP packaging, or output validation when needed.
- Do not use any model-based image generation, drawing, or creative image production capability. Do not call `image` or `image_generate`, including list/status calls. The PNG files must be rendered from the original PDF by `scripts/render_pdf_pages.py`, not generated by a model.

## Workflow

1. Confirm the user is asking for an SOW or proposal task.
2. Read `references/feishu-integration.md` for trigger recognition, attachment intake, reply layering, and smoke-test behavior.
3. Read `references/workflow.md` for the end-to-end SOW workflow.
4. Read `references/sow-schema.md` before producing `sow-extraction.json`.
5. Read `references/review-guardrails.md` before finalizing any content.
6. Read `references/golden-sample-standard.md` only when the user explicitly provides or discusses a golden sample.
7. For revision messages, read `references/revision-workflow.md`.
8. Read `references/proposal-template.md` only if `scripts/render_sow_outputs.py` is unavailable.
9. For the 709 Riversdale Road demo, read `references/709-case-notes.md` only when needed for the demo context.
10. For a new SOW, run the Feishu preflight intake before rendering drawings or generating files.
11. Confirm these proposal header fields with the user: client name, quote ID/revision, project name, site address, and proposal date.
12. Confirm at least one readable drawing attachment is available: customer joinery/cabinetry drawing or architectural drawing.
13. If any required header field or drawing attachment is missing, ask one concise follow-up and stop. Do not start PDF rendering or SOW generation.
14. After the user confirms the preflight summary, generate or reuse a `sow_id`.
15. If an existing SOW workspace is available, call `scripts/sow_state.py outputs-status`. If outputs already exist, return them instead of re-reading the PDF.
16. For PDF drawings, render pages to PNG and visually review the rendered pages before extracting room scope.
17. After rendering, read `render-manifest.json`. If `page_count_truncated` is true, rerender with a higher `--max-pages` value before visual review.
18. Build `intermediate/drawing-index.json` with `scripts/build_drawing_index.py` and use it to confirm page coverage and page title candidates.
19. Produce `sow-extraction.json`, then immediately call `scripts/render_sow_outputs.py --docx` to produce `proposal.md`, `proposal.docx`, `open-questions.md`, and `feishu-summary.md`.
20. Call `scripts/package_sow_outputs.py` to produce a single SOW ZIP and `output-manifest.json`.
21. Return the contents of `feishu-summary.md` with the ZIP file as the primary deliverable. If Feishu ZIP upload fails, say so explicitly and send the five core files individually or offer email ZIP delivery. Do not hand-write a new long summary.
22. For revision messages, load the current SOW state when available, update the SOW JSON, reassemble the proposal, repackage the ZIP, and record the revision.

New SOW preflight rules:

- If the user supplies all required header fields and drawings in the initial message, summarize the detected values and ask for confirmation before generating.
- If only some fields are present, list only the missing fields and missing drawings. Do not ask the user to repeat information already provided.
- If the user replies with corrected header fields, update the preflight summary and continue only after confirmation.
- Do not create a customer-facing proposal with `Dear TBC`, standalone `TBC` header lines, or `Quote: TBC TBC`.

If optional scripts are used, call them with one direct interpreter command. Do not use `cd`, `&&`, `||`, pipes, redirection, or fallback shell snippets. If a script call would require shell chaining or fails once, continue with manual `sow_id` handling instead of retrying.

Do not ask the model to analyze a PDF path directly as an image. When the source is a PDF drawing, render the relevant pages to PNG first, then read the PNG files with the normal file `read` capability. The rendering step is mechanical only; all drawing understanding and SOW decisions must remain model-driven and reviewable.

When page images are needed, run `scripts/render_pdf_pages.py` with the direct Python invocation shown below. Do not ask for "image generation" or "generate an image"; this task is file conversion only. Do not call a separate visual-analysis helper for rendered PNG files; read each PNG file path directly.

For large drawing sets, keep the model output compact. After visual page review, write `intermediate/drawing-visual-notes.md` first, then write only `sow-extraction.json` manually. Do not manually write `proposal.md`, `proposal.docx`, or `open-questions.md`; render them with `scripts/render_sow_outputs.py --docx`.

Time budget rules for Feishu runs:

- Keep `intermediate/drawing-visual-notes.md` concise: one short line per reviewed page, plus room-level summary bullets.
- Keep `sow-extraction.json` concise: short descriptions, short evidence notes, no page-by-page prose copied into JSON.
- Prefer room-level evidence over repeating long evidence on every scope item.
- Cap top-level `open_questions` to the most important 12 questions unless the user asks for exhaustive detail.
- After `sow-extraction.json` is written, do not read more reference files unless validation fails.
- Always use `render_sow_outputs.py --docx` for Markdown, DOCX, and summary generation.
- If `sow_state.py outputs-status` reports `return_existing_outputs`, send the existing files immediately.
- If it reports `render_outputs_then_return`, run `render_sow_outputs.py --docx`, run `package_sow_outputs.py`, and send the ZIP without reprocessing drawings.

## Optional Scripts

- `scripts/sow_state.py`: create or load `sow_id` state, maintain workspace paths, and append revision history.
- `scripts/render_pdf_pages.py`: render PDF drawing pages to PNG for visual model review. It must not OCR, parse drawings, identify rooms, or extract scope.
- `scripts/build_drawing_index.py`: extract embedded PDF text into a page index for page count, drawing numbers, and area title candidates. It must not OCR, extract scope, or decide inclusions.
- `scripts/render_sow_outputs.py`: render `proposal.md`, optional `proposal.docx`, `open-questions.md`, and `feishu-summary.md` from an already-created `sow-extraction.json`. It must not interpret drawings or decide scope.
- `scripts/render_docx.py`: convert already-rendered `proposal.md` to simple `proposal.docx`. It must not interpret drawings or decide scope.
- `scripts/package_sow_outputs.py`: package the five core files plus `output-manifest.json` into one ZIP and write explicit workspace/package/delivery refs. It must not interpret drawings or decide scope.
- `scripts/validate_sow_outputs.py`: validate output artifacts for required files, basic JSON shape, open questions, and no final price leakage.
- `scripts/smoke_v03.py`: local v0.3 plumbing smoke test for rendering, DOCX, output status, revision metadata, and validation. It must not interpret revision text or modify SOW business content.
- `scripts/smoke_v04.py`: local v0.4 delivery smoke test for ZIP packaging, manifest, TBC boundary, DOCX header/footer/logo, and validation.
- `scripts/smoke_v05.py`: local v0.5 delivery and quality smoke test for workspace output, Feishu flat-download fallback, TBC/exclusion conflict warnings, and high-risk scope downgrade.

If PDF rendering fails because no renderer backend is available, report the blocker and do not claim that SOW outputs were generated.

Allowed `sow_state.py` commands are `init`, `show`, `outputs-status`, and `append-revision`. Do not call a `create` command.

Safe invocation pattern:

```text
python3 /absolute/path/to/skills/kitchman-sow/scripts/sow_state.py init --workspace /absolute/path/to/sow-workspace --project-name "709 Riversdale Road" --channel feishu --date 20260426
```

PDF render invocation pattern:

```text
python3 /absolute/path/to/skills/kitchman-sow/scripts/render_pdf_pages.py --pdf /absolute/path/to/input.pdf --output-dir /absolute/path/to/sow-workspace/intermediate/rendered-pages/doc-001 --max-pages 100 --dpi 160
```

Drawing index invocation pattern:

```text
python3 /absolute/path/to/skills/kitchman-sow/scripts/build_drawing_index.py --pdf /absolute/path/to/input.pdf --render-manifest /absolute/path/to/sow-workspace/intermediate/rendered-pages/doc-001/render-manifest.json --output /absolute/path/to/sow-workspace/intermediate/drawing-index.json
```

Markdown render invocation pattern:

```text
python3 /absolute/path/to/skills/kitchman-sow/scripts/render_sow_outputs.py --input /absolute/path/to/sow-workspace/output/sow-extraction.json --output-dir /absolute/path/to/sow-workspace/output --docx
```

ZIP package invocation pattern:

```text
python3 /absolute/path/to/skills/kitchman-sow/scripts/package_sow_outputs.py --output-dir /absolute/path/to/sow-workspace/output
```

Do not add or call document-processing scripts that interpret document contents unless the user explicitly changes the technical direction.

## Expected Outputs

Minimum output set:

```text
sow-extraction.json
proposal.md
proposal.docx
open-questions.md
feishu-summary.md
```

Primary delivery file:

```text
<project-slug>-sow.zip
```

The ZIP contains the five core customer-facing files plus `output-manifest.json` as a technical traceability manifest.

Feishu response should be layered:

1. Task confirmation.
2. Attachment/source summary.
3. SOW completion summary.
4. Key room preview.
5. Open questions summary.
6. ZIP package file.
7. ZIP content list.
